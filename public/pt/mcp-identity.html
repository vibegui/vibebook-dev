Seu MCP sabe quem chama.
Sem ninguém colar token.

Quando uma sala do vibebook se liga ao seu servidor MCP (aba Apps ou connect_mcp), cada chamada diz quem está olhando e de qual sala, assinada pelo vibebook. Seu servidor confere a assinatura e decide o que essa pessoa pode fazer.

Como funciona

Toda requisição do vibebook ao seu MCP, inclusive o initialize, traz o header X-Vibebook-Identity: um JWT assinado em EdDSA (Ed25519), válido por 5 minutos.

isshttps://vibebook.dev
sub, emailo email de quem está olhando (ou de quem é o Claude que chamou)
roomo id da sala de onde veio a chamada
auda URL do seu MCP exatamente como foi conectada no vibebook
iat, expemitido agora, vence em 5 minutos
jtiid aleatório de cada token
headeralg: EdDSA e o kid da chave

A chave pública está em vibebook.dev/.well-known/jwks.json. A privada nunca sai do vibebook.

Seu servidor também tem login próprio? Responda 401 com o WWW-Authenticate do MCP. Cada pessoa entra uma vez pela aba Apps, e o vibebook segue o caminho padrão: RFC 9728 (resource metadata) → RFC 8414 (authorization server) → registro dinâmico de cliente → PKCE S256. O vibebook guarda esse acesso selado, por pessoa, e manda Authorization: Bearer junto com a identidade nas chamadas seguintes. Ninguém cola token, e nada disso chega ao navegador, a um iframe ou a um Claude.

Como aceitar com segurança

  • Verifique a assinatura com as chaves da JWKS. Guarde em cache e, pra um kid desconhecido, busque de novo no máximo uma vez por minuto.
  • Aceite só EdDSA; nunca none nem HS*.
  • iss igual a https://vibebook.dev, exatamente.
  • aud igual à URL do seu próprio MCP, exatamente. Assim um token feito pra outro servidor não serve no seu.
  • exp no futuro (até 30 s de folga de relógio).
  • Depois, mapeie email (e room, se fizer sentido) pras permissões que você já tem. Email desconhecido: 403 ou visão pública.
  • Sem header válido: 401, ou só o que é público. Nunca confie num email que venha do corpo, de outro header ou de argumento de tool.
  • Tools que escrevem: guarde os jti vistos até o exp e recuse um repetido.

A identidade diz quem é. O que essa pessoa pode fazer, quem decide é o seu servidor.

Em TypeScript, com jose

import { createRemoteJWKSet, jwtVerify } from "jose";

// vibebook's public keys, cached; an unknown kid refetches at most once a minute.
const VIBEBOOK_KEYS = createRemoteJWKSet(new URL("https://vibebook.dev/.well-known/jwks.json"), {
  cacheMaxAge: 60 * 60 * 1000,
  cooldownDuration: 60 * 1000,
});

// MY_URL = this server's MCP URL exactly as it was connected in vibebook (scheme, host and path).
export async function vibebookIdentity(req: Request, MY_URL: string) {
  const token = req.headers.get("x-vibebook-identity");
  if (!token) return null;
  try {
    const { payload } = await jwtVerify(token, VIBEBOOK_KEYS, {
      issuer: "https://vibebook.dev",
      audience: MY_URL,
      algorithms: ["EdDSA"],
      clockTolerance: 30,
    });
    return { email: String(payload.email ?? payload.sub), room: String(payload.room ?? "") };
  } catch {
    return null; // bad signature, wrong iss/aud, expired: not vibebook
  }
}

Conferido contra tokens de verdade do vibebook: o válido passa; aud errado, iss errado e assinatura alterada falham.
